# Adding a service to the fleet

Bifrost's Apps/Jobs tabs, promote/rollback, and build-status badges are all
driven off one file: `internal/registry/registry.yaml`. Adding a service
there is bifrost's entire side of onboarding — a single YAML entry, no Go
changes, no rebuild required (it's read at process start, so a live pod
needs a restart to pick up a new entry). Everything else — the app's own CI,
its Kubernetes manifests, its GCP identity/secrets, and its ArgoCD
`Application`s — is plumbing that lives outside this repo. This doc draws
that line explicitly so a future onboarding doesn't have to rediscover it.

## 1. The registry entry (bifrost owns this)

Add a top-level key to `internal/registry/registry.yaml`, named exactly what
you want the service called everywhere in the UI (Apps tab, Jobs tab,
`<name>-staging`/`<name>-prod` namespace lookups, GitHub links, Cloud Build
trigger lookups):

```yaml
my-service:
  repo: my_service            # optional — see below
  urls:
    staging: https://my-service-staging.tailc06f30.ts.net
    prod: https://my-service.ethanswan.com
  preview:                     # optional — omit unless onboarding to previews too
    ...
```

Fields, per `internal/registry/registry.go`'s `Service`/`URLs`/`Preview`
types:

- **`repo`** (optional) — the GitHub repo name, when it differs from the
  service name (e.g. `asset-manager`'s repo is `asset_manager`). Omit it and
  the service name is used unchanged. This feeds `Registry.RepoFor`, which
  bifrost uses to build the "view commit" link next to a deployed SHA — get
  it wrong and that link 404s, but nothing else breaks.
- **`urls.staging`** / **`urls.prod`** (both optional) — the public URL for
  the "open ↗" link on that environment's card. Leave a field (or the whole
  `urls:` block) empty for a service with no ingress on that environment —
  `comms`, a background worker, has neither.
- **`preview`** (optional, entirely separate concern) — present only if the
  service should be part of `ib preview up`. See
  [`docs/preview-environments.md`](preview-environments.md) for its
  `neon`/`env`/`required` fields and the env-template resolution cascade; a
  service with no `preview:` block simply isn't a preview candidate, and
  everything above still works without it.

That's it on bifrost's side. The moment this entry merges and the running
pod restarts, the service appears in the Apps tab (`Registry.Names()` drives
that list directly) and in the Jobs tab, reading `<name>-staging`/
`<name>-prod` — even before any of the infrastructure below exists, just
with pods/images showing as unknown/absent until it does.

If you also want a Cloud Build status badge and pipeline link on the card,
GCP builds must find a Cloud Build trigger literally named `<name>-build`
(the registry key, not `repo` — see `cmd/bifrost/main.go`'s
`gcb.TriggerIDs` wiring) — one of the "outside bifrost" pieces below. This
only applies at all if `GCP_PROJECT` is set (`k8s/base/configmap.yaml`);
leave it unset fleet-wide to disable build badges entirely.

## 2. Everything else (bifrost doesn't own this)

Bifrost assumes conventions rather than configuring around them (see the
README's "Architecture" section): each service deploys to `<name>-staging`
and `<name>-prod` namespaces, its ArgoCD `Application`s are named
`<name>-staging`/`<name>-prod` and pin images via
`spec.source.kustomize.images`, and images are tagged by commit SHA. None of
that is generated by bifrost — it has to already be true in the new
service's own repo and cluster footprint before its registry entry means
anything beyond an empty card. This repo's own `k8s/` tree
(`k8s/base`, `k8s/staging`, `k8s/prod`, `k8s/argocd`) is the reference
pattern; bifrost's manifests carry some bifrost-specific extras (its own
`rbac.yaml` grants it cluster-wide pod/Application read+patch access — that
is *not* a convention every service needs, it's what bifrost itself
requires to be the fleet's dashboard).

Concretely, per service, outside this repo:

- **A Cloud Build trigger** (`<name>-build`) in the app's own repo, wired to
  its `cloudbuild.yaml`, pushing SHA-tagged images to Artifact Registry.
  Named to match the registry key (see above) if you want the CI-build
  column to populate.
- **A `k8s/` tree in the app's own repo** — `base`/`staging`/`prod` overlays
  and an `argocd/applications.yaml` following the namespace/Application
  naming convention above. Someone still has to
  `kubectl apply -f k8s/argocd/...` once to bootstrap those `Application`
  objects into the `argocd` namespace — ArgoCD doesn't discover new repos on
  its own.
- **ArgoCD Image Updater** config (an `argocd-image-updater.argoproj.io`
  annotation or `ImageUpdater` resource, per `k8s/argocd/image-updater.yaml`
  for the pattern) so staging auto-bumps to the newest build; prod stays
  manually promoted through bifrost.
- **Pulumi (a separate infra repo)** provisions the GCP side: the workload
  identity service account (`<name>-staging-sa@...`/`<name>-prod-sa@...`,
  referenced by the k8s `ServiceAccount`'s `iam.gke.io/gcp-service-account`
  annotation), any Secret Manager secrets the app needs plus the
  `SecretProviderClass` wiring to mount them, and the Cloud Build trigger
  itself.
- **OAuth client registration** with the identity provider, if the service
  authenticates users.
- **The public hostname** — a Cloudflare Tunnel entry, in this deployment —
  for anything with a `urls.staging`/`urls.prod` link above to actually
  resolve.

If the service is also going to be previewable, add a `preview:` sub-block
per step 1 above, then follow "Onboarding a new previewable app" in
[`docs/preview-environments.md`](preview-environments.md#onboarding-a-new-previewable-app)
for the two additional preview-only pieces (a `cloudbuild-preview.yaml` and
a `{repo}-preview-build` trigger). That's strictly additive to everything
above — a service is a normal fleet member first, previewable second.

## Gotcha: `ib.py`'s own service list

`ib.py`, the CLI wrapping bifrost's preview API, keeps its own hard-coded
service list independent of this registry — deliberately, since it has to
keep working when bifrost itself is down. Adding a service here does **not**
update `ib.py`; if the new service needs `ib preview`/`ib promote` support,
that list needs a separate, manual edit in `ib.py`'s own repo.
